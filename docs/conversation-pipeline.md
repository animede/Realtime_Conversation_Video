# 会話パイプライン解説

このアプリの会話パイプラインが「なぜこの形なのか」を説明する文書です。何が動くかは [README](../README.md) に、キャラクター描画側の仕組みは [Realtime_Narration_Video のテクニカルガイド](https://github.com/animede/Realtime_Narration_Video/blob/master/docs/technical-guide.md) にあります。本稿は設計判断の理由に絞ります。

## 1. 全体像と役割分担

```
ブラウザ                Realtime Conversation Video          外部
┌──────────────┐        ┌──────────────────────────┐
│ マイク → VAD │──WAV──>│ 会話の脳:                 │──chat──> LLMサーバ
│ テキスト入力 │──text─>│  ROLE注入・履歴・畳み込み │  (OpenAI互換,
│ SSE購読      │<──SSE──│  ストリーミング受信       │   input_audio対応)
└──────┬───────┘        │  返答確定後:              │
       │                │  POST /narrations         │──text──> r-n-v (8782)
       └────動画/音声────────────────────────────────────────┘  TTS+動画生成
```

会話の脳（ROLE、履歴、要約、LLM 呼び出し）はこのアプリが持ち、声と映像（TTS、動画チャンク生成、プリセット）は r-n-v が持ちます。境界は「返答テキストの受け渡し」1点だけです。この分離により、会話側の改良が描画側に波及せず、逆も然りです。

## 2. 返答経路から ASR を外す

音声入力の一般的な構成は「ASR → テキスト → LLM」の直列です。本アプリはこれを採らず、VAD が切り出した WAV を `input_audio` として **LLM に直接渡します**（[main.py](../app/main.py) の audio-turn）。

理由は2つあります。第一にレイテンシです。直列 ASR は返答開始前に文字起こしの完了を待たせます。第二に品質です。ASR の誤認識はテキストになった時点で確定し、LLM は誤ったテキストから返答するしかありません。音声を直接聞く LLM は、文脈から曖昧な発話を解釈でき、韻律の情報も失われません。

文字起こし自体は行いますが、**表示と履歴のためだけに、返答ストリームと並列で**走ります（[llm.py](../app/llm.py) の `transcribe`）。失敗しても `None` を返すだけで、会話は音声直入力で継続します。つまり文字起こしは会話の補助情報であって、依存関係ではありません。

この「文字は補助」という関係は、出力側も対称です。LLM が出力したテキストは画面に補助表示されるだけで、ユーザーが見るのはキャラクタの映像と声です。返答の正本は音声合成に渡るテキストなので、基本指示では Markdown・絵文字・記号列など読み上げで雑音になる要素を禁止しています。文字を主表示にしないからこそ、この読み上げ最優先の割り切りが成立します。

## 3. ブラウザ側 VAD

発話の切り出しはブラウザ内で完結します（[mic.js](../static/mic.js)）。energy(RMS) と ZCR のハイブリッド判定、250–4000 Hz のバンドパス前処理、無音 900 ms で区切り、260 ms 未満の断片は破棄、プリロール6フレーム、出力は WAV(PCM16 mono) です。

サーバー側 VAD にしなかったのは、判定のために音声を常時サーバーへ流し続ける構成にしたくなかったからです。ブラウザ内で完結すれば、ネットワークに乗るのは確定した発話セグメントだけで、無音時のトラフィックはゼロです。

## 4. ターンの進行

1会話は同時に1ターンだけ処理します（busy ゲート、進行中の送信は 409）。ターン内の並行構造は次のとおりです。

- LLM ストリーミング受信 → 差分を即 SSE でブラウザへ（`reply_delta`）
- ユーザー音声の文字起こし（音声ターンのみ）→ **マイク入力から VAD が切り出した、そのターンのユーザー発話の WAV 全体**を、返答とは別の一回きりの LLM 呼び出しに渡す。完了次第 SSE（`user_text`）。返答ストリームには一切関与しない（ストリームから文を切り出す処理は本アプリには無く、それは r-n-v 側のチャットモードの仕組み）
- 返答確定後 → 履歴確定・長文なら裏で要約（`summarize_later`）・r-n-v へ投入

失敗はすべて SSE の `error` イベントでユーザーに理由が届きます。裏で黙って死なないことを優先しています。

## 5. 履歴の保持と畳み込み

履歴は3層です（[conversation.py](../app/conversation.py)）。

1. **直近ターンは原文のまま**（`MAX_HISTORY`、既定4ターン）
2. **あふれた古いターンはローリング要約へ機械的に畳む**（「ユーザー: …」「キャラ: …」の80文字整形。LLM は使わない）
3. **長い返答だけ LLM 要約に差し替え**（`SUMMARY_THRESHOLD_CHARS` 超のみ、裏で生成し次ターンから効く）

畳み込みは毎ターンではなく**バッチ**で行います（`HISTORY_FOLD_BATCH_TURNS`、既定3ターン分たまってから一括）。これは次節の KV キャッシュのためです。

ローリング要約に LLM を使わないのは意図的です。この規模の履歴では機械的整形で文脈保持に十分であり、LLM 要約をゼロにすることで、後述するキャッシュ汚染源とホットパス外の失敗経路を丸ごと消せます。

## 6. KV キャッシュを守る設計

会話が伸びるほど、LLM の応答開始時間はプロンプト評価（prefill）に支配されます。プレフィックスキャッシュが効けば前回までの評価結果を再利用できますが、**効かせるための条件は運用設計で決まります**。本アプリは次の原則で組んでいます。

**原則: キャッシュドメインの境界はサーバプロセスである。** KV キャッシュはサーバプロセスごとに存在します。会話プロンプト以外のリクエスト（要約など）を同じサーバに投げると、会話プレフィックスのキャッシュがスロットから追い出され、次のターンで丸ごと再 prefill になります。ここで重要なのは、**計算競合とキャッシュ追い出しは別の劣化**だということです。前者は同時に走った瞬間だけ互いに遅くなる一時的なコストで、後者は毎ターン効き続ける持続的なコストです。GPU を分けるかどうかは前者の話であり、キャッシュ保護に必要なのはプロセスを分けることです。高性能な GPU なら、1台に2つのモデルサーバを載せてポートで分けても、キャッシュ隔離は完全に成立します。

この原則を、本アプリでは次のように適用しています。

- **ローリング要約は LLM を呼ばない**（前節）。畳み込みがキャッシュに触れる機会そのものがない
- **畳み込みのバッチ化**。要約は system プロンプト内にあるため、畳むたびにプレフィックスが要約位置から先で割れる。バッチ化により割れるのは N ターンに1回で、間のターンは履歴が追記のみ=プレフィックス完全安定（実測: 20ターン中の system 変化が毎ターン畳みの16回 → 5回）
- **system の先頭は不変**。基本指示 + ROLE が先頭にあり、会話中はバイト単位で安定。要約はその後ろに置く
- **動的情報（現在日時）はプレフィックスに置かない**。キャラが時間の質問に答えられるよう現在日時を渡しているが、注入先は**ターン末尾のユーザーメッセージだけ**。末尾は毎ターン新規の未キャッシュ領域なので、生きた時刻を入れてもキャッシュに影響しない（system に書けば毎ターン割れる）。履歴には元のユーザーテキストだけが残るため、過去ターンの日時行がプレフィックスを汚すこともない
- **描画側は会話サーバに触れない**。r-n-v への投入は朗読（LLM バイパス）経路なので、動画・TTS 側から LLM リクエストは一切発生しない
- **長文返答の要約差し替えは一度割れる**。差し替え時は履歴中の1メッセージが変わり、その位置から先で一度キャッシュが割れる（短い返答をプロンプトで指示する運用と併用する前提）
- **文字起こし・長文要約は会話と同じサーバに行くが、スロットが守る**。文字起こしは `input_audio` 対応モデルを要するため実質同居になる。一見すると上の原則と矛盾するが、llama-server の KV キャッシュは `--parallel` で確保した**スロット単位**で保持され、リクエストはプレフィックス類似度で既存スロットへ割り当てられる（`--slot-prompt-similarity`）。会話とは全く異なる system で始まる文字起こしは別スロットに落ち、会話プレフィックスを保持するスロットは無傷で残る。つまりサーバプロセスの内側に、スロットという一段細かいキャッシュドメインがある。ただし前提は**スロット2以上**。スロット1では音声ターンのたびに会話キャッシュが破壊されるうえ、同時に投げる文字起こしと返答が直列化してレイテンシも壊れるため、音声入力を使う構成では `--parallel 2` 以上を実質的な動作要件と考えるべき。プロセス分離は、サーバ実装のスロット挙動に依存しない強い保証として依然有効

## 7. 動画への受け渡し

返答テキストの**全文が確定してから、1回の POST で** r-n-v の朗読エンドポイント（`POST /api/sessions/{id}/narrations`）へ投入します。チャンク単位の逐次投入ではありません。文単位への分割、TTS、音声とチャンクの編成、動画生成のパイプライン化は、全文を受け取った r-n-v が内部で行います。直前ターンの生成が終わっていない場合は 409 が返るため、1秒間隔で最大30回粘ります。

LLM ストリーム中に文単位で逐次投入しない設計は、境界を「確定テキスト1点」に保つための割り切りです。返答は短く指示する運用なので、確定待ちのコストは小さく収まります。

## 8. 初回応答のレイテンシ予算

「話し終えてから、キャラが話し出すまで」は3つの区間の和です。

1. **発話の確定**: 無音 900 ms（VAD の区切り判定。これより短くすると発話中の息継ぎで切れる）
2. **返答の生成**: LLM ストリーミング。短い返答の指示と、前述のキャッシュ設計で prefill を抑える
3. **最初の映像と音声**: r-n-v がターン先頭チャンクだけ低解像度・少ステップで生成し、約2.6秒で初動を出す。以降のチャンクは再生の裏で生成されるため見えない。この技法は [r-n-v テクニカルガイド 7.1節](https://github.com/animede/Realtime_Narration_Video/blob/master/docs/technical-guide.md#71-ターン先頭チャンクの低解像度化会話初動を決めるレバー) を参照

2番目以降のチャンクの生成時間は再生に隠れるため、体感を決めるのはこの3区間だけです。それぞれ独立したレバー（VAD の無音閾値 / 返答長の指示とキャッシュ / 初回チャンクの解像度）で調整できます。
